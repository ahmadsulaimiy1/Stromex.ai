# StromeX Modern Auth — Bug-Fix Report

Real defects found and fixed while building and testing this phase, in the
order discovered.

## 1. Guest sentinel email rejected by response validation (fixed)

**Symptom:** `GET /auth/me` for a freshly created guest account crashed
with a `500`-class `ResponseValidationError` instead of returning the
account.
**Cause:** the guest account's generated address used a `.local` domain
(`guest-<uuid>@guest.stromex.local`). Pydantic's `EmailStr` validator
treats `.local` as an RFC 6762 reserved name and rejects it outright —
not merely "unreachable," genuinely invalid — and `UserRead` validates on
serialization, so every response involving a guest account failed.
**Fix:** switched the sentinel domain to `guest.stromex.ai` (a subdomain of
the app's own real domain) — still guaranteed to never be a real mailbox,
but a normal, valid-looking address that passes validation.

## 2. Alembic migration's downgrade left a stale Postgres ENUM type (fixed)

**Symptom:** `alembic downgrade -1` followed by `alembic upgrade head`
failed with `psycopg.errors.DuplicateObject: type "auth_token_purpose"
already exists`.
**Cause:** Alembic's autogenerated `downgrade()` drops the `auth_tokens`
table but — this is a known Alembic/Postgres gap, not specific to this
migration — does **not** automatically drop the Postgres `ENUM` type that
backs the table's `purpose` column. A downgrade followed by a re-upgrade
tried to `CREATE TYPE` something that still existed.
**Fix:** added an explicit `sa.Enum(name='auth_token_purpose').drop(...)`
to the migration's `downgrade()`. Verified with a full
downgrade → upgrade → downgrade → upgrade round trip before considering the
migration done.

## 3. Anonymous unique-constraint name would have broken downgrade (fixed)

**Symptom:** none yet observed, but real risk. Alembic's autogenerated
migration used `op.create_unique_constraint(None, 'users', ['google_sub'])`
— passing `None` lets Postgres pick an autogenerated name — and then
`op.drop_constraint(None, 'users', type_='unique')` on downgrade, which
cannot resolve `None` to a real constraint name.
**Fix:** gave the constraint an explicit name (`uq_users_google_sub`) in
both `create` and `drop`.

## 4. `d8`-signature — N/A carryover check

No dexing/signing issues this phase; the existing `apps/android/build.sh`
pipeline handled the new intent-filter and `singleTask` launch mode
without any changes to the toolchain itself. Confirmed via a full rebuild
and `apksigner verify`/`bundletool validate` pass (see the verification
report).

## Confirmed *not* a bug: rate limiting during the QA run

The extended `apps/android/qa/android_qa.mjs` run initially showed the
new email-verification check failing with no backend log entry for the
test account at all. Investigation showed the account's own `POST
/auth/register` call had been silently rejected by the same per-IP
register rate limiter from the original security audit (5/hour) — the
light+dark QA passes earlier in the same run had already used most of that
allowance. This is the limiter working exactly as designed against a
test harness making unusually many registrations in a short window, not a
product defect. Fixed the *test script* to clear the relevant Redis keys
before this section, matching the same pattern already used (and already
documented as "not a bug") in the original Android delivery's bug-fix
report.

## Confirmed *not* a bug: Google embedded-WebView sign-in restriction

Not something to "fix" — a deliberate design constraint, not a defect:
Google's own terms disallow completing OAuth sign-in inside an embedded
WebView (the component that renders every other screen of this app). The
"Continue with Google" button therefore opens the system browser rather
than navigating the in-app WebView there — see
`docs/10-STROMEX-AUTH-FEATURE.md` for the full explanation and why this
also happens to mean no AndroidX dependency was needed.

## Outstanding — not fixed, disclosed

- **Settings page mobile layout is cramped** (fixed 224px sidebar on a
  393px viewport) — pre-existing in `AppShell` since the original MVP, not
  introduced this phase, not fixed this phase either. See the test report.
- Everything else listed as "not verified" in
  `docs/11-STROMEX-AUTH-TEST-REPORT.md` is a coverage gap from missing
  infrastructure (a real Google Cloud OAuth Client, a real device/emulator,
  a real SMTP provider) rather than a known-broken behavior left in place.
